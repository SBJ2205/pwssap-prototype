(`phase-<number>-<short-title>`). Read this file first if you are
picking this project up without prior conversation context.

## Phase 1 — what exists now

Backend (`backend/`):
- `domain/enums.py` — `SubjectType`, `RunStatus`, valid/odd/even semesters
  (3/5/7 odd, 4/6/8 even — semesters 1-2 are out of scope), working days.
- `domain/timeslots.py` — canonical Mon-Fri x 4-slot grid, generated by
  `build_canonical_grid()`. Encodes the fixed hard rules: Monday slot 1
  is blocked for everything, slot 4 is lab-only every day, theory never
  uses slot 4.
- `domain/models.py` — `Subject`, `Teacher`, `TeacherSubjectCapability`,
  `TeacherAvailability`, `Student`, `ChoiceTagConfig`,
  `StudentChoiceSelection`, `Meeting`, `Section`, `GenerationRun`. No
  department/branch field anywhere (this app is department-scoped).
- `domain/validation.py` — `validate_subject`, `validate_teacher`,
  `validate_student`, `validate_semester`, `validate_slot_for_subject_type`,
  `validate_choice_tag_configs`. All return `List[str]` (empty = valid) so
  CSV row-level validation in later phases can reuse them directly.
- `data/store.py` — `InMemoryStore` rewritten around the new models.
  Starts empty except for the canonical time-slot grid; no fabricated
  demo subjects/students/teachers (real data arrives via CSV in Phase
  2-4). Has CRUD-ish methods already shaped for what those phases need:
  `upsert_subject`, `upsert_teacher`, `add_teacher_capability`,
  `set_teacher_availability`/`is_teacher_available`, `upsert_student`,
  `set_student_choice_selections`, `add_section`, `create_run`.
- `api/meta.py` — only `/health`, `/timeslots`, `/semesters` so far.
- `api/deps.py` — unchanged; the `X-Role` header stub for local
  demo-mode admin/student/teacher role-gating is still valid for later
  phases (see product decision #14).
- `tests/test_domain.py` — plain-assertion sanity checks (no pytest
  installed yet) for the grid rules, semester validity, and the
  validators above. Run with:
  `venv\Scripts\python.exe -m tests.test_domain` (from `backend/`).

## What was intentionally removed

The previous prototype ("blind abstract time-slot rating" model, no CSV
ingestion, no subject tags, no semesters, department fields on
Student/Teacher) does not match the actual product spec, so it was
removed rather than patched:
- `data/seed.py` (fabricated demo roster/sections — replaced by "real
  data comes from CSV" in later phases)
- `api/catalog.py`, `api/preferences.py`, `api/admin.py`,
  `api/solver_routes.py`
- `solver/engine.py`, `solver/helpers.py`, `solver/heuristics.py`,
  `solver/service.py`

The CP-SAT modeling approach in the old `solver/engine.py` (decision
variables per student/subject, reified assignment booleans for capacity
and no-clash constraints, a per-student penalty cap, OR-Tools CP-SAT) is
still a reasonable *starting point* for Phase 9, but the objective and
constraint shapes must change to match the new spec: time-slot
satisfaction first, faculty preference second (weighted lower), teacher
load balancing third (a real optimization term, not a cosmetic pass),
plus teacher availability as a hard constraint and lab section
parallelism (Phase 8) instead of student-driven section pruning.

## Known gap after Phase 1

The **frontend is now disconected from the backend** — it still calls
the old `/subjects`, `/students`, `/prefs`, `/solve`, etc. endpoints and
expects the old response shapes. This is expected: Phase 1 is backend
data-model-only. Frontend rework starts alongside the API endpoints
Phase 2+ introduces (subject list/choice-tag config UI in Phase 2,
CSV import UIs in Phase 3-4, etc.) — do not treat the current frontend
as a regression, it simply hasn't been touched yet.

## Next phase (Phase 2)

Subject CSV import + admin choice-tag configuration:
- CSV parser for `subject_code, subject_name, subject_tag, semester,
  type, weekly_hours, capacity, slot_structure/linked_pattern` producing
  row-level validation errors (reuse `domain/validation.validate_subject`).
- Store subjects via `InMemoryStore.upsert_subject`.
- An endpoint (and later UI) for the admin to see the distinct set of
  `subject_tag` values present for the semester being configured, mark
  any subset of them `is_choice_based=True`, and assign each a unique
  numeric value — persisted as `GenerationRun.choice_tag_configs` via
  `InMemoryStore.create_run` (validate with
  `validate_choice_tag_configs`). Remember: no fixed limit on how many
  tags can be choice-based, and the mapping is only valid for that run.
